# 款图库管理 产品方案 PRD

- 版本：v1.3（2026-07-19；Q1/Q4-Q6 已定；款级图明确为正反面双视角图，自动拼接产生）
- 状态：已确认，可进入 M1 开发
- 关联页面：工作台（`/`，InputsPanel 款号选择器旁）
- 关联代码：`backend/routers/styles.py`（现有只读接口）、`backend/db.py`、`frontend/src/components/InputsPanel/InputsPanel.tsx`

---

## 1. 问题陈述

`ai-supply/款图/` 是设计生图的唯一原始款图来源，但目前只能通过文件管理器手工维护：往根目录放 `{款号}.jpg` 正面图、往 `{款号}/` 文件夹放色号图。没有品类信息、没有上传时间记录、没有搜索——款数上来之后，用户在工作台选款前无法确认"这个款进库了吗、色号全不全、是什么品类"，出错只能靠生图失败后倒查文件夹。

系统里已有 `GET /api/v1/styles` 只读扫描该文件夹并供给工作台款号下拉，本需求是给这个只读库补上**写入（上传）与元数据（品类/时间）管理能力**。

## 2. 目标

1. 用户不离开工作台即可完成新款入库（正面图 + 色号图），上传后款号下拉立即可选。
2. 每个款有品类（两级）与上传时间记录，可按款号关键字、品类筛选查找。
3. 存量款（界面上线前已在文件夹里的）可被识别并补录品类，不需要迁移文件。
4. 文件夹目录结构保持现状不变，下游（工作台生图、orchestrator 的 ref_image_path / color_folder 引用）零改造。

## 3. 非目标

- **不替代文件夹作为图片事实来源。** 图片仍存在 `ai-supply/款图/`，SQLite 只存元数据。用户直接往文件夹拖文件依然有效（进入"待补录"状态，见 5.3）。
- **不做款图删除的级联清理。** v1 删除仅做引用提示，不自动清理历史 run/task 引用。
- **不接 ERP/商品系统同步。** 品类与色名均为人工录入，外部系统对接留待后续。
- **不改造选款中心（/selection）的上传。** 选款中心管理的是"确认上架的 SKU 图"（含 AI 生成图），与本库（原始参考款图）是漏斗的两端，v1 不合并。
- **不做图片编辑/裁剪/压缩。** 原图直存。

## 4. 用户故事

- 作为运营，我想在工作台款号下拉旁点「+新增」上传一个新款的正面图和色号图，这样不用切到文件管理器、也不会放错目录。
- 作为运营，我想给已有款追加色号图，这样补色时不需要记住文件命名规则。
- 作为运营，我想按款号搜索、按品类筛选库里的款，确认某个款是否已入库、有几个色。
- 作为运营，我想看到每个款的上传时间，判断哪些是本波段新进的款。
- 作为运营，我想看到哪些款"缺正面图"或"未录品类"，在生图前把数据补齐（缺正面图的款在工作台选不出来）。

## 5. 需求

### 5.1 P0 — 新增上传弹窗

入口：工作台 InputsPanel 款号 Select 旁「+新增」按钮；COLLECTION_2SKU 模式下上装/下装两个款号选择器旁也各放一个，三处共用同一弹窗（访客只读态均不显示，与现有 isGuest 逻辑一致）。

数据模型口径（2026-07-19 修正）：入库主体是 **SKU（款号 × 色号）**，每个 SKU 必须有**正面图 + 背面图**两张；款号（item id）与色号（sku id）可手填现成编号，留空则系统自动生成唯一 ID。

表单：

| 字段 | 必填 | 说明 |
|---|---|---|
| 款号（item id） | ✅ | 可填现成款号；留空自动生成 `IT{YYMMDD}-{2位序号}`（如 IT250719-01，序号按当日已有款递增）。实时查重——已存在则切换为"追加色号"模式（展示已有色号列表） |
| 大类 | ✅ | 单选：童装 / 男装 / 女装 / 运动 / 男睡衣 / 女睡衣（已定，2026-07-19） |
| 小类 | ✅ | 单选：上装 / 下装 / 整套装 |
| SKU 列表 | ✅ ≥1 条 | 每条 = 色号 + 色名 + 正面图 + 背面图，四项均必填。色号留空自动生成 `C01/C02…`（款内递增） |

落盘规则（平铺 + `_back` 后缀，存量零迁移）：

- 正面：`款图/{款号}/{色号}（{色名}）.{ext}` —— 与 `styles.py` 现有括号解析规则一致
- 背面：`款图/{款号}/{色号}（{色名}）_back.{ext}`
- 款级双视角图：`款图/{款号}.jpg` 是**正反面双视角款图**（一张图同时含正面+背面视图，step 2.1 款式结构分析的必需输入，见 `prompts/step2/01_style_analysis.md`）。上传时默认取**第一个 SKU 的正面图+背面图左右拼接**自动生成（白底、正面在左背面在右）；管理弹窗可更换（选其他色号重拼，或直接上传现成双视角图）

验收标准：

- [ ] 提交成功后：文件按上述路径落盘；SQLite 写入元数据（品类两级、created_at）；款号下拉（`["styles"]` query）invalidate 后立即出现新款。
- [ ] 款号/色号留空时自动生成 ID，且与文件夹、DB 中已有编号不碰撞（含并发上传场景）。
- [ ] 每条 SKU 缺正面或背面任一张均不可提交（必填约束仅针对新入库，存量款见 5.3）。
- [ ] `styles.py` 扫描色号时过滤 `_back` 后缀文件，不计入色号数、不出现在色号下拉；`GET /styles/{style_no}` 的 colors 条目新增 `back_url` 字段。
- [ ] 双视角图拼接：白底、正面在左背面在右、两图等高缩放；拼接失败视为上传失败整体回滚。
- [ ] 追加色号模式下不覆盖已有双视角图；追加的色号与已有重名时报错拦截。
- [ ] 单文件 >20MB、非 jpg/png/webp 拦截并提示（对齐 selection 上传的限制）。
- [ ] 上传失败（磁盘/权限）时给出明确错误，不写入半截数据（先落文件后写库，写库失败回滚删除文件）。

### 5.2 P0 — 库管理弹窗

入口：「+新增」旁「🗂 管理」按钮，打开大弹窗（宽 ~76vw，对齐现有详情弹窗规格），不新增路由。

- [ ] 列表展示全部款：正面图缩略图、款号、大类/小类、色号数、上传时间（存量款显示"—"或文件 mtime，标注来源）。
- [ ] 搜索框：款号关键字模糊匹配；筛选器：大类、小类。
- [ ] 每行操作：「追加色号」（复用 5.1 追加模式）、「编辑品类」（行内改两级品类）。
- [ ] 状态徽标：`缺封面`（根目录无 {款号}.jpg，工作台不可选）、`缺背面`（任一色号无 _back 图，标注缺几个）、`待补录`（文件夹里有但 SQLite 无记录）、`无色号`（color_count = 0）。
- [ ] 每行操作补充：「更换双视角图」（选任一色号正+反重新拼接，或直接上传现成双视角图，覆盖 {款号}.jpg）、「补背面图」（按色号逐张补传）。
- [ ] 分页或虚拟滚动，500 款不卡。

### 5.3 P0 — 存量款对账（folder ↔ DB）

SQLite 是元数据库，文件夹是图片事实来源，二者必然出现不一致：

- [ ] `GET /styles` 返回时以文件夹扫描结果为准，LEFT JOIN 元数据；无元数据的款标记 `meta_missing: true`（前端显示"待补录"）。
- [ ] DB 有记录但文件夹已被手工删掉的款：列表不显示，但管理弹窗提供"清理失效记录"入口（P1 可降级为自动清理）。
- [ ] 存量款补录品类后，created_at 记补录时间，另存 `source: backfill` 与文件 mtime 供参考。
- [ ] "正反面必填"仅约束新入库；存量款缺背面图不阻塞任何功能，仅显示 `缺背面` 徽标（后续可由背面图工具批量补齐）。

### 5.4 P1

- 删除款/删除单个色号图：删除前检查 runs/tasks 是否引用过该款路径，有则弹确认（仅提示，不阻断）。
- 批量补录：管理弹窗支持多选款批量设置品类。
- 上传即校验图片可读性（PIL open 一次），防止损坏文件进库导致生图失败。

### 5.5 P2（架构预留）

- 品类枚举走配置表而非硬编码，为后续男装/女装/运动的标签体系（对齐模板库项目）留口。
- 元数据表预留 `note`、`status`（在售/停用）字段。
- 对接选款中心：从款图库直接"选款入仓"，统一漏斗入口。

## 6. 数据与接口设计

新表（`backend/db.py`）：

```sql
CREATE TABLE IF NOT EXISTS style_meta (
  style_no      TEXT PRIMARY KEY,
  category_main TEXT NOT NULL,          -- 童装/男装/女装/运动/男睡衣/女睡衣
  category_sub  TEXT NOT NULL,          -- top/bottom/onepiece
  created_at    TEXT NOT NULL,          -- 入库/补录时间
  source        TEXT NOT NULL DEFAULT 'upload',  -- upload | backfill
  file_mtime    TEXT                    -- backfill 时的文件修改时间，仅参考
);
```

接口（扩展 `backend/routers/styles.py`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/styles` | 现有扫描 + JOIN style_meta，新增 category_main/sub、created_at、meta_missing、missing_back_count 字段（向后兼容，工作台现有调用不受影响） |
| GET | `/api/v1/styles/{style_no}` | colors 条目新增 `back_url`（匹配 `_back` 文件）；扫描时过滤 `_back` 不当色号 |
| POST | `/api/v1/styles/upload` | multipart：款号（空=自动生成 IT{YYMMDD}-NN）、两级品类、SKU[]（色号可空=自动 C 序号、色名、front、back 均必填）；落盘+自动拼接款级双视角图+写库 |
| PATCH | `/api/v1/styles/{style_no}/meta` | 编辑/补录品类 |
| POST | `/api/v1/styles/{style_no}/cover` | 更换双视角图：指定色号（服务端取其正+反重拼）或直传现成双视角图，覆盖 {款号}.jpg |
| POST | `/api/v1/styles/{style_no}/back` | 按色号补背面图 |
| DELETE | `/api/v1/styles/{style_no}` | P1；查引用后删文件+删记录 |

ID 生成：服务端在上传事务内生成——款号取当日 `IT{YYMMDD}-` 前缀最大序号 +1（同时查文件夹与 DB）；色号取该款下 `C` 前缀最大序号 +1。

写接口纳入现有公网守卫（访客 403），对齐 selection 路由的权限模型。

## 7. 成功指标

- 领先：上线 2 周内新款 100% 经界面入库（文件夹手工放图归零，以"待补录"新增数≈0 衡量）；上传成功率 ≥ 95%。
- 滞后：因"文件命名错/漏正面图"导致的生图失败归零；存量款品类补录完成率 4 周内 ≥ 90%。
