# 账单 Tab —— Token 消耗统计方案与看数逻辑（PRD v1）

> 状态：方案评审稿（不含实现）
> 范围：Step2 设计管线（2.1 ~ 2.8）+ Step3 生图的消耗统计与账单视图

---

## 1. 问题陈述

系统每天产生大量 LLM 调用（设计管线）和生图调用（gpt-image-2），但消耗数据散落在 trace 文件和任务表里，没有统一的账单视图。用户无法回答三个基本问题：**这次交付花了多少钱、钱花在哪个环节、这个月一共花了多少**。缺乏看数入口导致成本不可控、prompt 优化（如款级缓存、v4 token 瘦身）的收益无法量化。

## 2. 核心概念：交付任务（Delivery）的统计口径

**一次完整交付任务 = 一个 step2 主 run + 它的 fork 链 + 所有以它们为源的生图任务。**

```
交付任务（Delivery）
├── step2 主 run（2.1 → 2.2×N → 2.3 → 2.4/2.4s → [2.4.5] → 2.5/2.5L → 2.6 → [2.7/2.8]）
├── fork run 1..n（parent_run_id 链上的重跑，只计真跑节点）
└── 生图任务 1..n（generation_tasks.source_step2_run_id ∈ 上述 run 集合）
```

归集规则（按此顺序判定）：

| # | 规则 | 说明 |
|---|---|---|
| 1 | 以**主 run**（无 parent_run_id 的 run）为交付任务锚点 | fork run 沿 parent_run_id 向上归并到主 run |
| 2 | 生图任务按 source_step2_run_id 归到对应 run，再归到主 run | 一个交付任务可有多个生图任务（补跑/重生） |
| 3 | 每个 run / 任务的消耗**只计自己真实发生的调用** | 缓存命中（⚡fork 缓存 / ♻️款级缓存）计 0 token，但在明细中显式标记，用于展示"缓存节省" |
| 4 | 失败的 run / 失败的节点，已消耗的 token **照常计入** | 烧掉的钱不因失败而消失 |
| 5 | dry-run 计 0 | 明细中标记 dry |

### 2.1 节点级统计范围

| 节点 | 类型 | 计费单位 | 备注 |
|---|---|---|---|
| 2.1 款式分析 | LLM | token in/out | 成套模式 ×2 款；款级缓存命中计 0 |
| 2.2 颜色识别 | LLM | token in/out × 色号数 | 同上 |
| 2.3 性别比规划 | LLM | token in/out | |
| 2.4 主题选择 / 2.4s 单主题 | LLM | token in/out | 按实际走的图计 |
| 2.4.5 母图案 Blueprint | LLM | token in/out | 仅收敛模式 |
| 2.5 单色设计 / 2.5L Look 联合设计 | LLM | token in/out × 色号/look 数 | 全管线最大头（输出重） |
| 2.6 分布审计 | 纯 Python | **0** | 展示但恒为 0，保证"2.1→2.6"链路完整 |
| 2.7 决策 | 纯 Python | **0** | 同上 |
| 2.8 局部重设计 | LLM | token in/out × 重设计色号数 | 仅发散模式触发 |
| 工作台修复调用（单色重识别 / 单色重设计） | LLM | token in/out | 归入所属 run 的对应节点行 |
| 生图（step3） | 图像 | **按张计费**（无 token） | 单价按尺寸档：1024² = $0.04，1024×1536 / 1536×1024 = $0.06 |

### 2.2 成本折算

- **LLM 成本** = input_tokens / 1M × 模型输入单价 + output_tokens / 1M × 模型输出单价
- **单价表**在「设置」页维护：`{模型名: {input_per_1M_usd, output_per_1M_usd}}`，默认给 gpt-5.5 占位价，用户可改；单价变更只影响之后的折算展示（token 数是事实，价是视图参数）
- **生图成本** = 沿用现有 `COST_PER_IMAGE` 尺寸档估算（已落库 total_cost_usd）
- 所有成本均标注「估算」，token 数为精确值

## 3. 数据源盘点（现状与缺口）

### 已有数据（零改造可读）

| 数据 | 位置 | 粒度 |
|---|---|---|
| 每节点 token in/out、耗时、缓存标记 | 各 run 目录 `trace.jsonl` 的 node_completed 事件 + 节点 IO JSON 的 tokens 字段 | 节点级（含 2.2 每色号、2.5L 每 look 一条） |
| run 级 token 合计、耗时、模式、款号、趋势、fork 关系 | DB `runs` 表 | run 级 |
| 生图张数、成功/失败、估算成本、每张耗时 | DB `generation_tasks` 表（results JSON） | 任务级 + 每张图 |

### 已知缺口（P0 需处理）

1. **失败 run 的 DB 汇总缺失**：run 失败时 `mark_run_finished` 不写 total_tokens——失败前烧掉的 token 只在 trace.jsonl 里。账单必须从 trace 聚合，不能只信 DB 汇总列。
2. **重生（regenerate）覆盖成本**：生图任务重生后 `total_cost_usd` 被本次成本覆盖，历史那次的钱丢了。账单按 results 里实际成功张数 × 尺寸档重算，并注明「重生前的历史消耗不可追溯」（P1 可加归档计数）。
3. **工作台修复调用**的 token 记录在 trace 追加事件里，格式与常规节点略不同，聚合器需兼容。

## 4. 统计方案（推荐 A，预留 B 演进）

### 方案 A（推荐起步）：读取时聚合，零写链路改造

新增账单聚合端点，实时扫描：DB `runs`（按 parent 链归并）→ 每个 run 的 `trace.jsonl`（节点级 token）→ DB `generation_tasks`（生图）。首次访问聚合后**按 run_id 结果缓存**（run 是不可变的，跑完后消耗不再变化，缓存永久有效；running 状态的 run 每次实时读）。

- 优点：历史 run 全覆盖（无需回填）、不动任何写链路、实现集中在一个读模块
- 缺点：首次打开账单页要扫 trace 文件（当前几十个 run，秒级；缓存后无感）
- 接口形态：`GET /billing/summary?from=&to=&mode=`（交付任务列表 + 合计）、`GET /billing/delivery/{run_id}`（节点级明细）

### 方案 B（数据量大后演进）：落表

新增 `billing_node_stats` 表，run 结束时把节点级统计写库，历史用一次性回填脚本（复用 A 的 trace 解析器）。**A 的接口不变，只换数据源**——所以先做 A 不会白做。

触发升级 B 的信号：run 数 > 500 或账单页打开 > 3 秒。

## 6. Goals / Non-Goals

**Goals**

1. 任何一次交付任务的总成本与节点级构成 3 次点击内可见
2. token 数 100% 来自 trace 事实数据（含失败 run），成本折算误差仅来自单价配置
3. 缓存命中的节省被显式呈现（量化款级缓存/fork 的价值）
4. 月度总成本可按模式/款号切片

**Non-Goals（本期不做）**

1. Step1 趋势报告导入的 token 统计（独立于交付任务口径，P2 单列一行即可）
2. 对接 OpenAI 账单 API 做真实账单核对（估算已够决策用）
3. 预算告警/配额限制（先看数，后管控）
4. 多用户/多团队维度（单机单用户）

## 7. 需求分级

**P0（账单可用的最小集）**：交付任务归集逻辑（run+fork+生图）；trace 节点级聚合器（兼容缓存标记/失败节点/修复调用）；视图 1 汇总表 + 视图 2 明细；单价表设置项；run 级结果缓存。

**P2**：方案 B 落表 + 回填；step1 导入纳入；预算提醒。

## 9. 验收标准（抽样）

- Given 一个成套 run（2 款 12 色 6 look）+ 2 个生图任务，When 打开账单明细，Then 节点表包含 2×2.1、12×2.2、1×2.3、1×2.4s、1×2.4.5、6×2.5L、1×2.6(0)，token 合计与 trace.jsonl 逐条求和一致
- Given 一个 fork run（2.4.5 起重跑），When 查看该交付任务，Then 主 run 计入全部真跑节点，fork 只计 2.4.5 + 2.5L，⚡缓存节点计 0 且被标记
- Given 一个 failed run（2.4.5 网络中断），When 查看汇总，Then 该交付任务出现在列表中且设计 token > 0
- Given 单价表把 gpt-5.5 输入价改为 2 倍，When 刷新账单，Then 所有历史成本按新单价重算（token 数不变）
